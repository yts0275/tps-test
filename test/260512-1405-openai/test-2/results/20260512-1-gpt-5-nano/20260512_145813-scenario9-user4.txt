다음 Workflow의 노드 흐름을 최대한 자세히 해설합니다. 그림에서 보이는 노드는 두 종류로 구분해서 이해하면 흐름이 명확합니다.

- 보라색 노드: 실제 작업 단위(액티비티) 혹은 도구를 나타내는 주 노드
  - start, SoftwareEngineer, CodeAnalyzer, Editor, swe_tool, end
  - plus 코드 분석 도구/편집 도구/테스트 도구처럼 보이는 보라색 하위 노드들: code_analysis_tool, code_edit_tool, test_tool

- 옅은 회색의 둥근 박스: 전환 이벤트나 조건(액션명)을 나타내는 흐름 포인트
  - analyze_code, edit_file, done, continue 등

- 점선으로 연결된 화살표: 이벤트에 의한 흐름 전개, 즉 특정 이벤트가 발생했을 때만 다음 노드로 이동함을 뜻합니다.

전반적 흐름 요약
- 시작은 start에서 SoftwareEngineer로 흐름이 넘어갑니다.
- SoftwareEngineer는 두 가지 주 흐름으로 분기하는 경향이 보이며, 각각의 흐름은 서로 다른 도구/단계를 거쳐 end로 도달합니다.
  1) 왼쪽 흐름(코드 분석 및 편집 흐름): analyze_code 이벤트를 통해 CodeAnalyzer로 진입 → 코드 분석 도구로 결과를 핸들링 → 완료(done) 이벤트를 통해 Editor로 진입 → edit_file 이벤트로 편집 수행 → code_edit_tool로 편집 도구를 사용 → test_tool로 검증 → 필요 시 재수정(다시 Editor로 돌아감) 혹은 완료 상태로 진행
  2) 오른쪽 흐름(SWE 도구 흐름): continue 이벤트를 통해 swe_tool로 진입 → end로 종료
- 최종적으로 end에 도달하면서 Workflow가 종료됩니다.

노드별 상세 흐름
- start → SoftwareEngineer
  - 워크플로우의 진입점으로, 엔지니어 역할의 시작 시점을 나타냅니다.
  - 이후 두 방향으로 분기가 가능해 보입니다(다음 단계의 이벤트를 트리거).

- SoftwareEngineer
  - 이 노드는 워크플로를 주도하는 역할로 보입니다.
  - 두 개의 주된 분기를 생성하는 것으로 해석됩니다.
    - 왼쪽 분기: 코드 분석/수정 사이클을 시작하는 트리거
      - 연결 이벤트: analyze_code(옅은 회색 박스)
      - 이 이벤트는 CodeAnalyzer로 전달됩니다.
    - 오른쪽 분기: SWE 도구를 수행하는 트리거
      - 연결 이벤트: continue(또는 비슷한 조건)
      - 이 이벤트는 swe_tool로 전달됩니다.
  - 노드 간 흐름은 점선으로 되어 있어, SoftwareEngineer가 조건에 따라 어떤 도구를 선택적으로 호출하는 컨트롤러 역할임을 시사합니다.

- analyze_code → CodeAnalyzer
  - 분석 이벤트 analyze_code가 발생하면 CodeAnalyzer로 흐름이 넘어갑니다.
  - CodeAnalyzer는 코드 분석을 실제로 수행하는 주된 단위로 이해됩니다.

- CodeAnalyzer
  - 코드 분석 작업을 수행합니다.
  - 다음 단계로 이동하기 위해 보라색의 code_analysis_tool에 결과를 넘기거나, done 이벤트를 통해 다음 단계(Editor)로 게이트합니다.
  - 흐름의 주기성: 분석이 끝나면 done이라는 전환 이벤트를 통해 다음 단계로 넘어가는 것이 특징입니다.

- done(코드 분석 완료) → Editor
  - CodeAnalyzer의 작업이 완료되었음을 나타내는 이벤트가 발생하면 Editor로 흐름이 넘어갑니다.
  - 즉, 분석 결과를 바탕으로 실제 코드 편집 단계로 넘어가는 시점입니다.

- edit_file → Editor
  - Editor 자체로 들어오는 또 다른 진입 신호로 보며, 편집하고자 하는 파일을 수정할 수 있는 트리거입니다.
  - 이 이벤트를 수용하면 Editor 내부의 편집 작업이 준비됩니다.

- Editor
  - 코드 편집을 담당하는 핵심 단계로 보입니다.
  - Editor는 편집 후에 다음 도구로 넘겨주기 위한 경로를 제공합니다.
  - 보통은 편집이 완료되면 code_edit_tool로 이동시키거나, 추가 검증(test) 등으로 이어질 수 있습니다.
  - 이 흐름에서 Editor는 code_edit_tool, test_tool 등과 연결되어 있어 편집 후의 실제 수정 도구 사용 및 검증 단계를 거칩니다.

- code_edit_tool
  - Editor에서 편집을 실제로 수행하는 도구를 나타냅니다.
  - 편집 작업이 끝나면 보통 테스트나 다음 단계로의 흐름으로 넘어가도록 설계됩니다.
  - 이 노드는 편집 결과를 시스템에 반영하는 역할을 합니다.

- test_tool
  - 편집된 코드의 테스트를 수행하는 도구입니다.
  - 테스트가 완료되면 다음으로의 흐름은 일반적으로 Editor(재수정 필요 시)나 end로 이어집니다. 다만 그림에서 테스트 도구 이후의 구체 흐름은 명확히 보이지 않으나, 보통은 테스트가 성공하면 흐름이 종료(end)로, 문제가 있으면 Editor로 재진입하는 루프 구성이 일반적입니다.

- swe_tool
  - SoftwareEngineer와 연결된 오른쪽 분기의 도구로 보이며, SWE 관련 작업을 수행합니다.
  - continue 이벤트를 통해 swe_tool로 진입하는 흐름이 표시되어 있습니다.
  - swe_tool 수행이 끝나면 end로 종료하는 경로가 구성되어 있습니다.

- end
  - 워크플로우의 종료점입니다.
  - 왼쪽 코드 분석/편집 흐름의 완료 또는 오른쪽 SWE 도구 흐름의 완료를 통해 최종적으로 도달합니다.

추가로 해석적 주의점
- 그림에서 보라색 노드가 실제 작업 단위이고, 회색의 박스는 호출되거나 이벤트가 발생하는 포인트로 이해하는 것이 가장 직관적입니다.
- 점선으로 연결된 화살표는 이벤트/조건에 의해 흐름이 나눠지며, 특정 이벤트(label)로만 다음 노드로 넘어간다는 뜻입니다.
- 왼쪽 흐름(Analyze → CodeAnalyzer → done → Editor → edit_file → code_edit_tool → test_tool)은 코드 분석에서 편집 및 테스트까지의 연속적인 파이프라인으로 해석할 수 있습니다.
- 오른쪽 흐름(SWE 도구 경로)은 SoftwareEngineer가 특정 상황에서 SWE 도구를 사용하도록 하는 보조 경로이며, end까지 직행하는 간단한 종료 경로로 보입니다.

요청하신 “노드 들의 흐름”에 맞춰 요약하면
- 시작은 SoftwareEngineer로 들어가고, 이후 두 가지 흐름 중 하나를 선택합니다.
  - 왼쪽 흐름: analyze_code → CodeAnalyzer → done → Editor → edit_file → code_edit_tool → test_tool → (재수정 여부에 따라 Editor로 돌아오거나) end
  - 오른쪽 흐름: continue → swe_tool → end
- end에서 Workflow가 종료됩니다.

원하시면 이 흐름을 실제 워크플로우 엔진의 스펙(예: BPMN, YAML 기반의 정의, 또는 그래프 데이터 형식)에 맞춰 구체적인 노드/경로 매핑으로 변환해 드리겠습니다.
