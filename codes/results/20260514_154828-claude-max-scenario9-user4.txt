## LangGraph 워크플로우 노드 흐름 분석

### 노드 구성

| 노드 | 유형 | 역할 |
|------|------|------|
| `start` | 진입점 (oval) | 워크플로우 시작 |
| `SoftwareEngineer` | 오케스트레이터 | 중앙 의사결정 에이전트 |
| `CodeAnalyzer` | 서브 에이전트 | 코드 분석 전담 |
| `Editor` | 서브 에이전트 | 코드 편집/테스트 전담 |
| `swe_tool` | 도구 노드 | SWE 범용 도구 실행 |
| `code_analysis_tool` | 도구 노드 | 코드 분석 도구 실행 |
| `code_edit_tool` | 도구 노드 | 코드 편집 도구 실행 |
| `test_tool` | 도구 노드 | 테스트 실행 도구 |
| `end` | 종료점 (filled circle) | 워크플로우 종료 |

---

### 전체 흐름 구조

```
start
  └─(solid)→ SoftwareEngineer
                ├─(analyze_code)─→ CodeAnalyzer
                │                     ├─→ code_analysis_tool ─(continue)─→ CodeAnalyzer (루프)
                │                     ├─(continue)─→ Editor
                │                     └─(done)─→ SoftwareEngineer
                │
                ├─(edit_file)─→ Editor
                │                 ├─→ code_edit_tool ─(continue)─→ Editor (루프)
                │                 ├─→ test_tool ─(continue)─→ Editor (루프)
                │                 └─(done)─→ SoftwareEngineer
                │
                ├─→ swe_tool ─(continue)─→ SoftwareEngineer
                │
                └─→ end
```

---

### 노드별 상세 흐름

#### 1. `start` → `SoftwareEngineer`
- 워크플로우가 시작되면 **무조건 `SoftwareEngineer`로 진입** (실선 엣지, 조건 없음)
- `SoftwareEngineer`는 전체 워크플로우의 **중앙 오케스트레이터** 역할

---

#### 2. `SoftwareEngineer` (핵심 분기점)
수신한 태스크를 분석하고 **4가지 경로 중 하나**를 선택 (모두 점선 = 조건부 엣지):

| 전이 레이블 | 목적지 | 조건 |
|------------|--------|------|
| `analyze_code` | `CodeAnalyzer` | 코드 분석이 필요한 경우 |
| `edit_file` | `Editor` | 파일 편집이 필요한 경우 |
| (없음) | `swe_tool` | 범용 SWE 도구 사용이 필요한 경우 |
| (없음) | `end` | 태스크가 완료된 경우 |

---

#### 3. `CodeAnalyzer` 서브그래프
`SoftwareEngineer`로부터 `analyze_code` 신호를 받아 활성화:

1. **`CodeAnalyzer` → `code_analysis_tool`** (점선)
   - 코드 분석 도구를 호출
2. **`code_analysis_tool` → `CodeAnalyzer`** (`continue`)
   - 도구 실행 결과를 받아 다시 `CodeAnalyzer`로 복귀
   - **내부 루프**: 분석이 완료될 때까지 반복 가능
3. 분석 완료 후 두 가지 출구:
   - **`done` → `SoftwareEngineer`**: 분석 결과를 오케스트레이터에게 반환
   - **`continue` → `Editor`**: 분석 결과를 바탕으로 직접 편집 단계로 이동

---

#### 4. `Editor` 서브그래프
`SoftwareEngineer`로부터 `edit_file` 신호를 받거나, `CodeAnalyzer`로부터 `continue`로 진입:

1. **`Editor` → `code_edit_tool`** (점선)
   - 실제 코드 편집 도구 호출
2. **`code_edit_tool` → `Editor`** (`continue`)
   - 편집 완료 후 `Editor`로 복귀 (내부 루프)
3. **`Editor` → `test_tool`** (점선)
   - 편집 후 테스트 실행
4. **`test_tool` → `Editor`** (`continue`)
   - 테스트 결과를 받아 `Editor`로 복귀 (내부 루프)
   - 테스트 실패 시 재편집 → 재테스트 반복 가능
5. **`done` → `SoftwareEngineer`**: 편집/테스트 완료 시 오케스트레이터에게 반환

---

#### 5. `swe_tool` 노드
- `SoftwareEngineer`에서 직접 범용 도구를 실행
- 실행 완료 후 **`continue` → `SoftwareEngineer`** 로 결과 반환
- `CodeAnalyzer`나 `Editor`를 거치지 않는 단순 도구 실행 경로

---

### 핵심 설계 패턴

1. **Hub-and-Spoke 패턴**: `SoftwareEngineer`가 허브, 나머지 노드가 스포크
2. **내부 루프 (ReAct 패턴)**: 각 서브 에이전트는 도구 호출 → 결과 수신을 반복하며 자율적으로 작업 완료
3. **계층적 에이전트 구조**: 오케스트레이터가 전략을 결정하고, 서브 에이전트가 전술(도구 호출)을 담당
4. **`done` vs `continue`**: `done`은 상위 오케스트레이터로의 복귀, `continue`는 동일 레벨 내 루프 또는 다음 단계로의 이동을 의미
