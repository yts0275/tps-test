이미지를 분석하여 각 노드의 흐름을 상세히 설명하겠습니다.

## LangGraph 워크플로우 상세 분석

### 전체 구조 개요

이 그래프는 **소프트웨어 엔지니어링 자동화 멀티에이전트 시스템**으로, `SoftwareEngineer`가 중앙 오케스트레이터(Orchestrator) 역할을 하고, 하위 전문 에이전트들에게 작업을 위임하는 구조입니다.

---

### 노드 구성

| 노드 | 역할 | 타입 |
|------|------|------|
| `SoftwareEngineer` | 중앙 오케스트레이터 | Agent Node |
| `CodeAnalyzer` | 코드 분석 전문 에이전트 | Agent Node |
| `Editor` | 코드 편집/테스트 전문 에이전트 | Agent Node |
| `swe_tool` | SoftwareEngineer 직접 도구 | Tool Node |
| `code_analysis_tool` | 코드 분석 도구 | Tool Node |
| `code_edit_tool` | 코드 편집 도구 | Tool Node |
| `test_tool` | 테스트 실행 도구 | Tool Node |

---

### 노드별 흐름 상세

#### 1. 진입점: `start` → `SoftwareEngineer`
```
start ──► SoftwareEngineer
```
- 그래프 실행이 시작되면 **항상 `SoftwareEngineer`로 진입**합니다.
- `SoftwareEngineer`는 요청을 분석하여 다음 4가지 경로 중 하나를 선택합니다.

---

#### 2. `SoftwareEngineer` (중앙 오케스트레이터)

`SoftwareEngineer`는 **조건부 엣지(conditional edge)** 를 통해 4가지 방향으로 분기합니다:

```
SoftwareEngineer ──[analyze_code]──► CodeAnalyzer
SoftwareEngineer ──[edit_file]────► Editor
SoftwareEngineer ──────────────────► swe_tool
SoftwareEngineer ──────────────────► end
```

| 전이 조건 | 대상 | 의미 |
|-----------|------|------|
| `analyze_code` | `CodeAnalyzer` | 코드 분석이 필요하다고 판단 |
| `edit_file` | `Editor` | 파일 편집이 필요하다고 판단 |
| *(직접 호출)* | `swe_tool` | 자체 도구 직접 사용 |
| *(종료 조건)* | `end` | 작업 완료 |

---

#### 3. `CodeAnalyzer` 서브그래프

```
CodeAnalyzer ◄──[continue]── code_analysis_tool
     │                              ▲
     │                              │
     └──────────────────────────────┘  (반복 루프)
     │
     ├──[done]──► SoftwareEngineer  (분석 완료 후 복귀)
     └──[continue]──► Editor         (분석 후 편집 필요 시)
```

**세부 흐름:**
1. `SoftwareEngineer`로부터 `analyze_code` 신호를 받아 진입
2. `code_analysis_tool`을 호출하여 코드 정적 분석 수행
3. 분석 결과가 불충분하면 → `continue`로 다시 `code_analysis_tool` 재호출 (루프)
4. 분석 완료 후:
   - `done` → `SoftwareEngineer`로 결과 반환
   - `continue` → 직접 `Editor`로 전달 (편집이 즉시 필요한 경우)

---

#### 4. `Editor` 서브그래프

```
Editor ◄──[continue]── code_edit_tool
  │                          ▲
  │     ◄──[continue]── test_tool
  │                          ▲
  │                          │
  └──(두 도구 모두 반복 호출 가능)
  │
  └──[done]──► SoftwareEngineer  (편집/테스트 완료 후 복귀)
```

**세부 흐름:**
1. `SoftwareEngineer`의 `edit_file` 또는 `CodeAnalyzer`의 `continue`로 진입
2. `code_edit_tool`을 호출하여 파일 수정 수행
3. `test_tool`을 호출하여 수정 결과 검증
4. 편집 → 테스트 → 재편집의 **반복 루프** 가능 (`continue`)
5. 작업 완료 시 `done` → `SoftwareEngineer`로 복귀

---

#### 5. `swe_tool` 경로

```
SoftwareEngineer ──► swe_tool ──[continue]──► SoftwareEngineer
```

- `SoftwareEngineer`가 하위 에이전트 없이 **직접 도구를 호출**하는 경우
- 도구 실행 완료 후 `continue`로 다시 `SoftwareEngineer`로 복귀
- `SoftwareEngineer`는 결과를 보고 다음 행동 결정

---

#### 6. 종료: `SoftwareEngineer` → `end`

```
SoftwareEngineer ──► end
```

- 모든 작업이 완료되었다고 판단하면 `end` 노드로 전이하여 그래프 실행 종료

---

### 전체 실행 시나리오 예시

```
start
  └─► SoftwareEngineer  (요청 분석)
        └─[analyze_code]─► CodeAnalyzer
              ├─► code_analysis_tool  (분석 반복)
              ├─► code_analysis_tool  (재분석)
              └─[done]─► SoftwareEngineer  (분석 결과 수신)
                    └─[edit_file]─► Editor
                          ├─► code_edit_tool  (수정)
                          ├─► test_tool       (테스트)
                          ├─► code_edit_tool  (재수정)
                          ├─► test_tool       (재테스트)
                          └─[done]─► SoftwareEngineer  (완료 보고)
                                └─► end
```

---

### 핵심 설계 패턴

1. **계층적 에이전트 구조**: `SoftwareEngineer`가 작업을 분해하고 전문 에이전트에게 위임
2. **ReAct 루프**: 각 에이전트(CodeAnalyzer, Editor)가 도구 호출 → 결과 확인 → 재호출을 반복
3. **결과 집계**: 하위 에이전트는 `done`으로 항상 오케스트레이터에게 결과를 반환
4. **유연한 라우팅**: `SoftwareEngineer`가 상황에 따라 다른 경로 선택 가능
